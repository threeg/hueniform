This brief scopes the next version of Hueniform. It is the v0.3.0 analogue of the project brief
and, once approved, drives a set of **deltas** against the living specification rather than a fresh
spec. The binding documents in `docs/` are not forked per version: they evolve in place, and `git`
(the `v0.2.0` tag) is the record of what shipped. v0.3.0 is a **presentation-layer** release and,
unusually for this project, carries **no requirement deltas** (§3) — the change is *how the app
looks*, not *what it does*.

---

## 1. Aim of v0.3.0

v0.3.0 is a **visual redesign** release. It applies the finished design in
`docs/designs/Hueniform App.html` — a warm, editorial look (cream paper ground, teal and
burnt-orange accents, a Georgia serif wordmark) — to the real React SPA, replacing the utilitarian
styling that emerged during v0.1.0/v0.2.0 implementation.

The redesign is **visual plus layout restructure**: the same screens, states, flows and routes as
today (upload/detect, confirm-and-correct, inventory, garment detail, outfit request, suggestion
results), but with each screen's *layout* reorganised to match the design, and a shared visual
language applied throughout. It does **not** introduce new screens, new interactions, or any change
to what the app computes or stores.

The meta-goal is unchanged: the process is a deliverable. The design is captured as a **binding
design-system document** (`docs/06-design-system.md`) extracted from the prototype, so that visual
decisions become part of the spec rather than living only in a one-off HTML file. The prototype
itself is retained as the visual reference.

The local-first contract is preserved. The redesign is pure frontend and adds no runtime network
calls — web fonts and assets are bundled at build time, not fetched at runtime. NFR-1 and NFR-8 are
unaffected.

## 2. Scope

### In scope

1. **A design system extracted from the prototype** — colour tokens (the cream grounds, teal and
   orange accents, neutrals), typography (the serif wordmark/display face and the body face), spacing
   and radius scale, elevation, and the shared component vocabulary (buttons, cards, chips/tags,
   swatches, form controls, navigation). Written to `docs/06-design-system.md`; realised in the SPA as
   CSS custom properties / CSS Modules per the existing frontend conventions.
2. **Restyle and re-lay-out every screen** to match the prototype, screen by screen: upload/detect,
   confirm-and-correct, inventory (grouped view), garment detail, outfit request, suggestion results —
   plus shared shell chrome (header/wordmark, navigation, empty/loading/error states).
3. **Update the wireframes** in `docs/04-wireframes/` where the new layout differs materially from the
   committed wireframes, so the wireframes and the shipped UI stay in agreement.
4. **A visual-fidelity test approach** — how the redesign is guarded (component tests updated for new
   structure; a visual-regression/snapshot approach if adopted; e2e journeys kept green through the
   restyle).

### Out of scope

- Any new feature, screen, interaction or setting.
- Any change to the matcher, services, API contract, or storage — no `FR`/`NFR` behaviour changes.
- Dark mode, theming beyond the single prototype look, and user-configurable appearance.
- The advanced roadmap items (weather-aware suggestions, wear tracking, hosting) — still deferred.

## 3. Requirement-change summary

**None.** v0.3.0 introduces no new `FR`/`NFR` and amends none. The redesign is a presentation-layer
change that preserves all v0.2.0 behaviour and contracts; the API contract (`docs/03-api-contract.md`)
and the numbered requirements (`docs/02-requirements.md`) are unchanged.

Two existing non-functional requirements are **re-affirmed and re-verified** rather than changed:

- **NFR-1 / NFR-8 (offline):** the redesign must ship all fonts and assets at build time — no runtime
  fetches.
- **NFR-6 (responsive at 500 garments):** the re-laid-out inventory must still render within budget.

The requirement-delta milestone (§5, M16) therefore exists **only to confirm this "no deltas"
finding and author the design-system doc** — if the run-through surfaces a genuine requirement need
(e.g. a contrast/accessibility floor worth pinning), it is raised there and `docs/02-requirements.md`
is amended before implementation, never silently.

## 6. Build approach

- **Design system first.** Author `docs/06-design-system.md` and realise its tokens/components before
  restyling any screen, so screens compose a shared vocabulary rather than each inventing its own.
- **One screen at a time, journeys stay green.** Each screen restyle is scoped to a single Code
  session and must keep `make test` (component + e2e) passing — the redesign changes structure and
  styling, so component tests that assert on brittle markup are updated in the same commit.
- **Pin the look where it is cheap to.** Where a visual-regression/snapshot tool is adopted (decided
  in M19), baseline snapshots are captured as part of the relevant ticket.
- **Prototype is the reference, design-system doc is binding.** Where the two disagree, the
  design-system doc wins (as with code vs the API contract); discrepancies are resolved into the doc,
  not left in the HTML.

## 7. Open questions for the design-system / wireframe passes

These do not block approval of this brief; they are settled in milestones 16–19.

1. **Token source of truth** — are the prototype's exact colours/spacing lifted verbatim, or
   normalised into a rounded scale? [M16]
2. **Fonts offline** — which faces the prototype uses, and confirming they can be bundled at build
   time without a runtime fetch (NFR-1/NFR-8). [M16]
3. **How far the layout restructures each screen** — which screens are a pure restyle vs a genuine
   re-lay-out needing a wireframe rewrite (M18). [M16/M18]
4. **Visual-regression tooling** — adopt a snapshot/visual-diff tool, or rely on updated component +
   e2e tests? [M19]
5. **Accessibility floor** — is a contrast/focus-visible standard worth pinning as an NFR, or handled
   as a ticket-level acceptance criterion without a numbered requirement? [M16]

## 8. Risks

| Risk | Notes / mitigation |
|---|---|
| Restyle churns component markup and breaks brittle tests | Update component tests in the same commit; keep e2e journeys as the behaviour anchor; restyle one screen per ticket. |
| A "visual-only" version quietly grows new behaviour | Hard scope line (§2): no new screens/interactions, no `FR`/`NFR` deltas; anything behavioural is raised as a requirement change first, or deferred to a later version. |
| Web fonts/assets introduce a runtime fetch | Bundle all fonts/assets at build time; re-verify NFR-1/NFR-8 offline in M16 and at implementation. |
| Re-laid-out inventory regresses performance at 500 garments | Re-check NFR-6 during the inventory restyle ticket. |
| Prototype and shipped UI drift | Capture the design in `docs/06-design-system.md` (binding) and update wireframes (M18) so there is a single agreed reference, not a stale HTML file. |
