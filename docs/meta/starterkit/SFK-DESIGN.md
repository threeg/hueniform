# Spec-First Kit — Design Log & Handoff Context

> **What this file is.** The design rationale, decision history, gotchas, and open ideas behind the
> Spec-First Kit (SFK). It exists so refinement can continue in a fresh thread/repo **without losing
> the reasoning** and without regressing hard-won decisions. It is a *maintainer* document for people
> building SFK — **not** part of the kit that gets dropped into a user's project.
>
> **Where it lives.** At the **SFK repo root**, alongside (not inside) the droppable payload, which is
> the **`kit/`** folder. A project consumes only the *contents of `kit/`*: `.sfk/`, `spec/`,
> `.claude/skills/`, and `.gitignore` (the root `CLAUDE.md` is generated by `sfk-init`). This
> `SFK-DESIGN.md` and the repo `README.md` stay at the repo root and are never copied into a project.
>
> **Source of truth vs this file.** The kit's own `kit/spec/README.md` is authoritative for *how the
> kit currently works*. This file records *why*, *what was rejected*, and *what's next*. When they
> disagree, the kit wins on behaviour; update this log.

---

## 1. Provenance & purpose

- SFK was **distilled from the Hueniform project** (`docs/meta/lessons-learned.md` and
  `method-improvements.md` there), whose meta-goal was "the development process is as much a deliverable
  as the software." SFK is that process, generalised and made project-neutral.
- **Purpose:** a drop-in starting point for building software **spec-first, ticket-by-ticket, with an
  AI coding agent**, driven by a small set of skills.
- **Two load-bearing principles:** (1) the specification is binding and comes first — no code until a
  fresh session could implement any ticket from the docs alone; (2) the ticket is the unit of work and
  *is* the prompt — one ticket, one commit.

## 2. Current state (inventory)

The kit payload (see `process/README.md` for the full picture):

- **Root:** lean `CLAUDE.md` (project standing instructions, auto-loaded), `.gitignore`; the project
  owns its own root `README.md`.
- **`.claude/skills/`** — seven skills (see §4): `sfk-init`, `sfk-version`, `sfk-next-milestone`,
  `sfk-signoff`, `sfk-next-ticket`, `sfk-verify`, `sfk-update-process`.
- **`process/`** — the living spec + workflow: `README.md` (the method guide), `milestone-plan.md`,
  per-milestone folders (`brief/`, `requirements/`, `architecture/` [architecture.md + api-contract.md],
  `wireframes/`, `test-strategy/`), `tickets/` (BOARD, CONVENTIONS, TICKET-TEMPLATE, CLAUDE.md),
  `templates/layer-CLAUDE.md`, optional `addons/meta-loop/`, and `.sfk/` (read-only kit machinery).
- **`process/.sfk/`** — `manifest.md` (kit identity: name, version `1.0.0`, author Gregg Seymour),
  `CHANGELOG.md` (per-kit-version changes; the update migration script), and `templates/` (the pristine
  read-only source of every living file).
- **Kit version:** `1.0.0`. **Not yet run on a real project.**

The eight steps (= the first version's milestones): brief → requirements → architecture & contract →
wireframes → test strategy → ticket generation → scaffolding → implementation.

## 3. Design principles (the ones to preserve)

- **Clean project root.** The kit lives under `process/` + `.claude/`; it never squats files the
  project owns (`README.md`, `CLAUDE.md`, code).
- **Living docs, not forked-per-version.** `process/` docs evolve in place; version tags record what
  shipped. Later versions run as a **delta pass**, not a fresh spec.
- **`.sfk/` is a read-only source.** Skills copy templates *out* of `process/.sfk/templates/` to their
  working locations and edit the copies; nothing edits inside `.sfk/` except `sfk-update-process`.
- **Human owns completion.** The agent drafts and commits, but only the user signs off a milestone
  (`sfk-signoff`).
- **Mode over brand.** Authoring (spec) vs building (code) is the durable distinction; Cowork/Code are
  just the current recommended tools.

## 4. Decision log (with rationale & rejected alternatives)

Newest-relevant first. Each entry: the decision, why, and what was rejected.

- **SpecKit-style split: `.sfk/` at root (machinery) + `spec/` at root (living docs).** *Why:* mirrors
  what SpecKit does with `.specify/` (templates/scripts it reads) and `specs/` (the artefacts it
  writes). The skills **read** from `.sfk/` and **write** into `spec/`. This makes machinery and working
  docs siblings, each obviously one thing, and keeps the kit's footprint in a real project to two hidden
  folders (`.sfk/`, `.claude/`) plus a generated `CLAUDE.md` and `.gitignore`. *Superseded:* the earlier
  layout where everything lived under `process/` with `.sfk/` nested inside it.

- **`process/` renamed to `spec/`.** *Why:* once `.sfk/` moved out, the folder is purely the visible,
  generated living docs — the analog of SpecKit's `specs/`. Singular `spec/` fits (one evolving
  specification, not per-feature). *Considered:* keeping `process/` (reinforces the "process is a
  deliverable" meta-goal); chose `spec/` for SpecKit familiarity.

- **"Read-only" is a convention, not a filesystem property.** A dotfolder is only *hidden*, not
  write-protected. `.sfk/` is kept untouched by the authoring skills through instructions
  ("copy out, never edit"); only `sfk-update-process` writes it. Enforcing real read-only (perms / git
  hook) was rejected — it would fight the update skill.

- **Repo structure: `kit/` wrapper + maintainer docs at root.** The SFK repo is `README.md` (project
  intro + usage example) + `SFK-DESIGN.md` (this log) + `kit/` (the droppable payload). A project takes
  only the contents of `kit/`. *Why:* keeps the payload clean and the maintainer docs out of users'
  projects.

- **Method guide lives at `spec/README.md` (kit-owned).** *Why:* discoverable in the working area where
  a human looks. *Alternative:* hiding it in `.sfk/` — rejected as less discoverable. Trade-off: it's a
  kit-owned file sitting in the otherwise user-owned `spec/`; `sfk-update-process` refreshes it.

- **Kit lives in `process/` + `.claude/`, not the repo root.** *Why:* the kit's README was squatting
  the project's own root README, and living docs got tangled with app code. *Rejected:* leaving
  templates at root; naming the folder `sfk/` (too cryptic) or `spec/` (undersells tickets/process).

- **Docs are not numbered** (`brief.md`, not `01-brief.md`). *Why:* they're living and evolve across
  versions; a number prefix implies a fixed sequence that stops being true. Ordering is owned by
  `milestone-plan.md`. *Exception:* point-in-time version briefs keep the version in the name
  (`vX.Y.Z-brief.md`).

- **Per-milestone folders**, topic-named, with the named master file binding and other files as
  supporting context (integration docs, inspiration). *Why:* gives each milestone a home for the
  material that informed it without polluting the master. *Rejected:* numbered milestone folders (same
  fixed-sequence problem).

- **Cowork for authoring, not Chat.** *Why:* Cowork has direct file access; Chat needs uploads and adds
  no value for these steps. Framed as a "mode (recommended tool)" so it ages well.

- **Meta loop (`addons/meta-loop/`) is OFF by default.** *Why:* for a normal project it's ceremony —
  empty retro docs on day one — and the per-layer `CLAUDE.md` "record pitfalls here" habit already
  captures practical lessons. It's opt-in for projects whose goal includes improving the method itself.
  (Note: this is for a *user's* project. SFK's own design log is *this* file.)

- **Every ticket opens with `## In plain English`.** *Why:* a jargon-free 1–2 sentence summary makes
  tickets legible to non-technical readers and is a scope sanity check. Applied to the kit's
  TICKET-TEMPLATE; deliberately **not** back-filled into Hueniform (kept isolated — see §6).

- **Seven skills, and why each exists:**
  - `sfk-init` — one-time environment bootstrap **only** (root CLAUDE.md, process structure,
    gitignore). *Rejected:* having init also start Milestone 1 — it was doing too much; starting
    milestones belongs to `sfk-version` + `sfk-next-milestone`.
  - `sfk-version` — starts a version: writes the version brief and lays down that version's milestone
    table. Added so the lifecycle is init (once) → version (per version) → milestones.
  - `sfk-next-milestone` — works one milestone to a **committed draft** and iterates on feedback.
    *Why commit WIP:* the user shouldn't have to commit; the agent keeps the record honest.
  - `sfk-signoff` — the human gate; the only thing that marks a milestone Complete and advances the
    plan. *Why separate:* mechanises "the agent never self-completes."
  - `sfk-next-ticket` — one ticket, one commit, during implementation.
  - `sfk-verify` — post-batch spec audit + quality review; ships as a **template** filled in for the
    stack at scaffolding (Milestone 7). *Why template:* the checks are stack-specific.
  - `sfk-update-process` — pulls a newer kit version into an existing project (see §5).

- **`sfk-` prefix on all skills.** *Why:* marks them kit-owned and avoids collisions with other skills.

- **`.sfk/` read-only + copy-out model.** *Why (bug-driven):* `sfk-init` was editing template files
  inside `.sfk/`. Fix: `.sfk/templates/` is the sole, read-only source; skills copy out and edit the
  copies. *Rejected:* `.template` sibling files next to each working file (noisier folders) — chose a
  hidden mirror dir instead.

- **Versioning = single kit version + CHANGELOG.** *Why:* one `kit_version` in `manifest.md` plus a
  changelog that doubles as the update migration script. *Rejected:* version numbers in filenames
  (churns every file each release, clutters the tree).

- **Manifest = kit identity only; project state lives in root `CLAUDE.md`.** *Why:* to keep `.sfk/`
  fully off-limits to the authoring lifecycle. The project's code (ticket prefix) and applied kit
  version are recorded in the root `CLAUDE.md` *Project & kit* section.

- **No default project version.** *Why:* the project decides where its versioning starts (`v0.1.0` or
  `v1.0.0` or anything). `sfk-version` uses exactly the number given; templates use a `<VERSION>`
  placeholder. (This was a real complaint: the kit had assumed `v0.1.0`.)

- **Thread-naming was removed.** *Why:* the agent can't rename Cowork threads programmatically, so the
  "as your first action, ask the user to rename this thread" step was just noise and often guessed the
  wrong name. Kept only a passive README tip. **Project code was kept** — it's the ticket prefix
  (`ACME-001`), needed regardless; `/sfk-init ACME` is an optional shortcut.

- **Neutral examples only.** `ACME` (and `WIDGET` where a second is needed). No `HUE`/Hueniform terms
  anywhere.

## 5. How `sfk-update-process` is meant to work

It is a **semantic migration, not a blind file copy** (a blind copy would clobber filled-in docs,
because the kit also ships working-named templates). It: compares the newer kit's `kit_version`
(its `.sfk/manifest.md`) against the project's applied version (root `CLAUDE.md`); reads CHANGELOG
entries newer than that (each entry carries an **Apply** note — refresh / add / amend / interview);
refreshes kit-owned files and the `.sfk/templates/` mirror; then for each living doc reasons three ways
(the user's file vs the *old* pristine vs the *new* pristine) and applies only the kit's delta,
interviewing where content is needed; offers (not forces) to backfill new template sections into
existing artefacts; and bumps the applied version in root `CLAUDE.md`.

## 6. Gotchas & constraints learned

- **Skill `description` frontmatter must not contain angle brackets** (`<...>`) — the loader treats
  them as XML tags and rejects the skill. Keep `<PLACEHOLDER>` tokens in the SKILL.md *body*, never the
  description.
- **Skill install differs by client.** Claude Code auto-discovers `.claude/skills/`. The Cowork desktop
  app does **not** — install via Settings → Capabilities, or package each skill dir as a `.skill` file
  (a zip of the skill directory containing `SKILL.md`) and use the Save-skill button.
- **`.skill` packaging** = zip the skill folder's contents so `SKILL.md` is at the archive root.
- **Authoring-environment quirks (relevant only when editing the kit inside a sandbox like this one):**
  file **deletion is blocked** (`rm`/`rmdir` fail) — you can only create, write, and `mv`/rename; and
  the `.claude/` path may be blocked for the Write tool (use bash to write there). Empty dirs and
  leftover files can accumulate; git ignores empty dirs so they don't ship.
- **Git auto-maintenance can leave lock files** (`.git/HEAD.lock`, `index.lock`, `objects/*.lock`) that
  the sandbox can't delete, blocking git. Mitigation used: `git config gc.auto 0`,
  `maintenance.auto false`, `fetch.writeCommitGraph false`; clear stray locks by renaming them aside.

## 8. How to keep refining SFK

- Treat `kit/spec/README.md` as the behavioural spec; when you change behaviour, update it and the
  relevant `SKILL.md`, then update `kit/.sfk/CHANGELOG.md` and this log.
- Keep the kit **neutral** (no real project names/terms) and keep skill **descriptions bracket-free**.
- When you change a living-file template, remember it lives in `kit/.sfk/templates/` (the source);
  the working copies are generated by the skills.
- Rebuild the `.skill` packages after editing any skill, if you use the desktop app.
- This file is SFK's own design log — the kit's `addons/meta-loop/` is for *users'* projects, not for
  SFK itself.
