# Spec-First Kit (SFK)

A drop-in way to build software **spec-first, ticket-by-ticket, with an AI coding agent** — a small set
of skills that interview you into a binding specification, turn it into a dependency-ordered ticket
queue, and then implement it one reviewable commit at a time.

| | |
|---|---|
| **Kit version** | v1.0.0 |
| **Author** | Gregg Seymour |
| **Status** | Early — usable, not yet battle-tested on a full project |

Inspired in shape by GitHub's SpecKit (a hidden `.sfk/` for machinery, a visible `spec/` for your
living documents), but built around an explicit **milestone lifecycle** with a human sign-off gate and
one-ticket-per-commit implementation.

## What's in this repo

```
/                       ← the SFK project (this repo)
├── README.md           ← this file — what SFK is and how to use it
├── SFK-DESIGN.md       ← design log & rationale (for people improving SFK itself)
└── kit/                ← THE DROPPABLE PAYLOAD — this is what a project consumes
    ├── CLAUDE.md?      ← (generated by sfk-init; not shipped)
    ├── .gitignore
    ├── .claude/skills/ ← the seven sfk-* skills
    ├── .sfk/           ← machinery: manifest, changelog, pristine templates (read-only)
    └── spec/           ← the method guide (spec/README.md) + empty milestone folders
```

Only the **contents of `kit/`** go into a project. The repo root (`README.md`, `SFK-DESIGN.md`, the
`kit/` wrapper) is for maintaining SFK and is never copied into a target project.

The two documents to read:

- **`kit/spec/README.md`** — the method guide: the eight steps, the milestone lifecycle, the skills, and
  how versions evolve. Read this to *use* the kit.
- **`SFK-DESIGN.md`** — the decision log: why the kit is shaped the way it is, what was rejected, known
  gotchas, and the backlog. Read this to *change* the kit.

## Installing into a project

1. **Copy the contents of `kit/` into your (empty) repository root** — so you get `.sfk/`, `spec/`,
   `.claude/skills/`, and `.gitignore` at the root.
2. **Make the skills available:**
   - **Claude Code (CLI):** they're already in `.claude/skills/` — discovered automatically.
   - **Cowork (desktop app):** skills aren't auto-discovered. Add them via **Settings → Capabilities**,
     or package each skill folder as a `.skill` file (a zip of the folder containing `SKILL.md`) and use
     **Save skill**.
3. **Drive the kit with the skills** (next section).

## How it's meant to be used — a worked example

Say you're starting a task manager called **ACME**. End to end:

**1. Bootstrap the environment.**

```
/sfk-init ACME
```

`sfk-init` asks a few essentials (stack, layers, command runner, UI y/n), then generates the root
`CLAUDE.md` and lays down the `spec/` skeleton by copying templates out of `.sfk/`. It records the
project code (`ACME`, your ticket prefix) in `CLAUDE.md`. It does **not** start any milestones.

**2. Start a version.**

```
sfk-version v0.1.0
```

(or `v1.0.0`, or whatever you choose — SFK never assumes a default.) You give it the version's goals;
it writes the version brief and lays down that version's **milestone table** in
`spec/milestone-plan.md` — the eight steps for a first release:

> brief → requirements → architecture & contract → wireframes → test strategy → ticket generation →
> scaffolding → implementation

**3. Work each milestone, one per session.**

```
sfk-next-milestone        # interviews you, drafts spec/brief/brief.md, commits it as a draft
# …you review; give feedback; it revises and re-commits until you're happy…
sfk-signoff               # you approve → it marks the milestone complete and advances
```

Repeat that pair through requirements, architecture, wireframes, test strategy, and ticket generation.
Each authoring milestone is its own `spec/` folder — drop supporting context (an integration's API
docs, wireframe inspiration) right in the folder beside the master file.

**4. Scaffold, then implement ticket by ticket.**

```
sfk-next-milestone        # scaffolding: repo skeleton, dependency-rule check, fills in sfk-verify for your stack
sfk-signoff

sfk-next-ticket           # implements the next ready ticket, one ticket → one commit
sfk-next-ticket
sfk-verify                # at a batch boundary: audits the batch against the spec, proposes cleanup tickets
…
sfk-signoff               # when all tickets are done and gates pass, sign off the implementation milestone
```

**5. Ship and iterate.** Tag the release, then `sfk-version v0.2.0` for the next round — later versions
run as a **delta pass** against the living `spec/` (new/changed requirements), not a rewrite.

**6. Pull kit improvements later.**

```
sfk-update-process        # compares your applied kit version to a newer kit and migrates your spec/ safely
```

After a couple of milestones, an ACME repo looks like:

```
acme/
├── CLAUDE.md                       ← standing instructions (project code ACME, dependency rule, DoD…)
├── .gitignore
├── .claude/skills/sfk-*
├── .sfk/                           ← untouched machinery
└── spec/
    ├── milestone-plan.md           ← M1–M3 ✅, M4 🔶
    ├── brief/brief.md              ← filled + signed off
    ├── requirements/requirements.md
    ├── architecture/architecture.md  api-contract.md  (+ your integration notes)
    ├── wireframes/…
    ├── test-strategy/…
    └── tickets/BOARD.md  ACME-001…  (as generation proceeds)
```

## The skills at a glance

| Skill | When | What it does |
|-------|------|--------------|
| `sfk-init` | once | Bootstrap the environment (root `CLAUDE.md`, `spec/` skeleton). Optionally takes the project code: `/sfk-init ACME`. |
| `sfk-version` | per version | Write the version brief and lay down its milestone table. No default version. |
| `sfk-next-milestone` | per milestone | Work the next milestone to a committed draft; iterate on your feedback. |
| `sfk-signoff` | per milestone | The human gate — mark it complete and advance. |
| `sfk-next-ticket` | during build | Implement the next ready ticket, one ticket per commit. |
| `sfk-verify` | at batch boundaries | Spec-audit + quality review; propose cleanup tickets. |
| `sfk-update-process` | on kit updates | Migrate an existing project to a newer kit version, preserving your content. |

## Principles (the short version)

- **Spec first, and binding.** No code until a fresh session could implement any ticket from the docs
  alone.
- **The ticket is the prompt.** One ticket, one commit; the work record and the code record stay 1:1.
- **The human owns completion.** The agent drafts and commits; only you sign off a milestone.
- **`.sfk/` is read-only machinery; `spec/` is yours.** Skills read templates from `.sfk/` and write
  your living docs into `spec/`.

See `kit/spec/README.md` for the full method and `SFK-DESIGN.md` for the reasoning.
